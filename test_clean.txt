5. Introduction  
 
This document describes the testing requirements and test plan for the MedPlus Pharmacy Point 
of Sale (POS) Management System . The system is designed to meet the business needs of 
MedPlus Pharmacy —a community pharmacy operating in Nairobi, Kenya. The objective is to 
automate manual pharmacy operations, including sales transaction processing, real -time medicine 
inventory tracking (with expiry monitoring), prescription record verification, customer loyalty records, 
and business reporting, thereby facilitating accountability, efficiency, and customer satisfaction. 
Testing is a major source of feedback and serves as a benchmark for ensuring the software is 
stable, secure, and compliant. Testing will be performed to verify that the system produces the 
desired results under various operating conditions. This test plan document identifies the software 
items to be tested, the testing environment, the test case design, and the test measurement 
techniques to be used. 
 
System Capabilities 
1. Process sales transactions for prescription and over-the-counter (OTC) medicines. 
2. Manage real-time medicine inventory, tracking expiry dates and batches. 
3. Record customer/patient profiles and track loyalty programs. 
4. Manage prescription records and enforce compliance by linking prescriptions to sales of 
prescription-only (Rx) medicines. 
5. Record suppliers and handle supply chain workflows via purchase orders. 
6. Provide role-based user access controls (Admin, Pharmacist, Cashier) with dynamic 
permission updates. 
7. Support modern payment interfaces, including Cash, Card, and M-Pesa STK push callbacks 
via Safaricom Daraja API. 
8. Generate daily, weekly, monthly sales reports, low-stock alerts, expiring stock reports, and 
profit-margin summaries. 
9. Automatically backup data and log system audit trails. 
Testing criteria will be utilized under the white-box, black-box, and system testing paradigms to 
ensure code correctness and operational compliance.

5.1 Goals and Objectives  
 
The main goal of testing is to compile a detailed document that will be used by developers and QA 
personnel to verify that the MedPlus system performs in accordance with the specifications in the 
System Requirements Specification (SRS) document. 
 
Testing Objectives 
Defect Identification: Uncover errors, bugs, security vulnerabilities, and failures in the 
database schema, API routing, and web UI. 
Test Case Standardization: Establish reusable test cases and test data representing 
realistic pharmacy scenarios (e.g., dispensing expired stock, checking out Rx drugs without 
prescriptions). 
Resource Optimization: Allocate testing resources (hardware, servers, testers, network 
setups) efficiently. 
Schedule Alignment: Establish a structured testing timeline across the different phases of 
unit, integration, validation, and system testing. 
Requirement Verification: Ensure all functional and non-functional requirements (including 
response times, uptime, database security, and compliance with the Pharmacy and Poisons 
Board of Kenya regulations) are met. 
Usability Assessment: Verify that the frontend web interfaces are intuitive, clear, and easy 
to use by pharmacy administrators, cashiers, and pharmacists. 
System Consistency: Ensure that database transactions adhere to ACID properties and 
that state management remains consistent during peak workloads or concurrent operations.

5.2 Statement of Scope  
 
The scope of testing covers the end -to-end functionality of the MedPlus Pharmacy POS system. 
This includes the client interface (served dynamically from the /web directory), the Go backend API 
application, database queries, and third -party integrations (PostgreSQL data structures, local 
configurations, and the Safaricom Daraja API for M-Pesa STK pushes). 
 
5.2.1 Major Constraints 
Network Dependencies: The M-Pesa payment integration relies on external callbacks from 
the Safaricom Daraja API. Testing requires mock callback payloads or sandbox endpoint 
availability. 
Platform Portability: The system must run reliably across different operating systems 
(Windows 10/11 for local pharmacy computers, and Linux for Docker containers and staging 
environments). 
Database Availability: Testing relies on a persistent connection to PostgreSQL. A database 
connection pool failure or local server downtime will suspend backend validation. 
Hardware Interfaces: Testing point-of-sale peripherals, such as physical USB barcode 
scanners and 80mm thermal receipt printers, requires physical devices or simulated inputs. 
 
5.2.1.1 Software to be Tested 
The software system under test is the MedPlus Pharmacy POS Management System , which 
consists of: 
• Backend API Application: Written in Go, exposing RESTful endpoints under /api/* for 
authentication, inventory, customers, prescriptions, sales, supply chain, payments, and reports. 
• Frontend SPA Web Client: A web interface built using HTML5, Vanilla CSS, and JavaScript, 
communicating with the Go backend. 
• Database Layer: PostgreSQL relational database schemas, indexes, checks, and foreign 
key relationships. 
 
5.2.1.2 Testing Strategy 
The testing workflow is structured incrementally to isolate errors efficiently: 
Unit Testing: Focuses on testing individual modules, functions, input fields, and database 
queries in isolation. 
Integration Testing: Evaluates the interaction between combined software units, such as 
Go handler routing, database queries, and third-party API communication. 
Validation Testing: Checks that the system functions in a manner that the pharmacy end 
users expect, validating workflows from the point of view of the cashier, pharmacist, and 
administrator. 
High-Order (System) Testing: Validates the system as a whole, including performance, 
security, data recovery, and user acceptance.

5.2.2 Integration Testing 
Integration testing verifies that the individual units of the system—such as the Go handlers, 
middleware validation, database layer, and Safaricom API integration—work together seamlessly. 
 
Functional Requirements Validated 
Session & Middleware Integration: Enforcing token-based authentication (JWT extraction, 
validation, and user role extraction) on private routes. 
Inventory Stock Adjustment: Automated inventory deduction upon sale processing 
(applying FIFO logic when multiple batches exist). 
Prescription-Sales Linkage: Verifying that checking out prescription-only (Rx) medicines 
requires a valid prescription record ID in the request payload. 
Purchase Order Stock Receipt: Automated stock quantity increment in products table once 
a draft purchase order status is updated to received. 
M-Pesa Payment Status Sync: Safaricom callback payload matching and updating the 
correct transaction record status from pending to completed or failed in the database.

5.2.4.1 Recovery Testing 
Recovery testing evaluates the system's ability to maintain data integrity and recover gracefully 
from sudden server, database, or network crashes. 
Go Server Crash Recovery 
Test: Kill the Go backend process during an active checkout API call. 
Result: The database transactions must roll back. Client receives a standard gateway error (or 
reconnects when the server restarts). 
Recovery Validation: On restarting the Go executable, verify database connectivity is restored 
automatically, database pools are rebuilt, and incomplete transactions show no partial writes. 
 
 
PostgreSQL Connection Lost Recovery 
Test: Terminate the PostgreSQL database service while the Go backend is running. 
Result: Backend logging registers connection loss. Accessing APIs returns 503 Service Unavailable 
with details logged. 
Recovery Validation: Once PostgreSQL service starts again, backend pinging logic (invoked via 
/api/ready) detects reconnect and queries succeed without requiring a server reboot. 
 
 
M-Pesa Webhook Callback Recovery 
Test: Simulate Safaricom sending an STK callback while the MedPlus server is offline. 
Result:  Safaricom  logs  delivery  failure.  The  transaction  remains  in  pending  state  in 
mpesa_payments. 
Recovery Validation: Admin dashboard allows manual status checks by querying Safaricom API 
/api/payments/mpesa/status/{checkoutRequestId} to resolve pending statuses.

5.2.4.2 Security Testing 
Security testing ensures the application protects pharmacy data, locks unauthorized access, and 
guards against security exploits. 
Role-Based Access Control (RBAC) 
• Verifies that cashiers cannot access /api/admin/* or /api/reports routes. 
• Attempting to access admin endpoints returns a 403 Forbidden JSON response. 
• Admin panel allows dynamic role-permission changes stored in the role_permissions table. 
 
Authentication & Session Management 
• Passwords are encrypted using bcrypt hashing before storage. Plaintext passwords are 
never logged or stored. 
• JWT tokens are signed using a secure algorithm and verified on each request. 
• Accounts are locked for 15 minutes after 5 consecutive failed login attempts to prevent 
brute-force attacks. 
 
Database Security & Input Validation 
• All SQL statements use parameterized placeholders (e.g. $1, $2) supported by the pq Go 
library, preventing SQL injection. 
• Input strings are sanitized on the backend and escaped on the frontend to prevent 
Cross-Site Scripting (XSS). 
• Cross-Origin Resource Sharing (CORS) is configured explicitly, restricting API access to 
registered domains in production.

5.2.4.3 Performance Testing 
Performance testing evaluates response times, concurrency limits, and database execution 
speeds. 
API Response Latencies 
• Under normal workloads (up to 5 concurrent cashier terminals), responses for product 
lookups, barcode identification, and cart checkouts must resolve in under 1.5 seconds. 
• Database queries are optimized using index tables on frequently searched fields: 
■ Barcode checks: idx_products_barcode on products(barcode) 
■ Category filters: idx_products_category on products(category) 
■ Transactions: idx_sales_transaction_id on sales(transaction_id) 
 
 
Concurrency Load Testing 
• Enforce database connection limit configurations (DB.SetMaxOpenConns(25)) to manage 
hardware resource consumption on the PostgreSQL container. 
• The Go backend handles requests concurrently using Goroutines, ensuring thread safety 
and preventing database locks.

5.2.4.4 Alpha/Beta Testing 
Prior to full deployment, testing is conducted by MedPlus Pharmacy staff in two phases: 
 
Alpha Testing (Internal) 
• Conducted by developers and the QA team in a staging environment using seeded demo 
data. 
• Verifies basic flows, API edge-cases, error message handling, and page response 
behaviors. 
Beta Testing (User Acceptance Testing) 
• Conducted by MedPlus Pharmacy staff (Admins, Pharmacists, and Cashiers) in the actual 
operating environment. 
• Staff register transactions, scan test barcodes, trigger test M-Pesa STK pushes (Sandbox 
mode), and export generated sales reports. 
• Feedback is gathered regarding interface usability, receipt print alignments, and system 
speed.

5.6 Test Record Keeping  
 
To track testing progress and ensure all issues are resolved, a detailed test logging process is 
maintained: 
Defect Tracking: Found defects must be recorded in an issue tracking sheet, specifying the 
module, description, severity, status, and developer assigned. 
System Log Files: Go backend errors and panic logs are captured and written to system 
files (server.log) for debug review. 
Database Audit Trails: Security-critical events (login failures, user deactivations, payment 
adjustments) are logged directly in user activity records to ensure compliance and 
traceability. 
Sign-off Report: A summary report documenting final test results, unresolved low-priority 
issues, and performance metrics is archived for design references.
