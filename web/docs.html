What the system does

MedPlus POS is a complete pharmacy operations system. It handles sales, cart and checkout, customer records, product inventory, supplier management, purchase orders, stock receiving, receipts, reports, analytics, and administration.

Who it is for

It is designed for pharmacies that need one connected system for front-desk sales, stock control, supplier coordination, and management reporting.

Why it matters

A completed sale updates inventory. A received purchase order increases stock. Reports and analytics read real operational data. This reduces manual work and keeps the business view accurate.

User Roles and Access

Access is controlled by permissions. A role is not just a label. Each role is connected to a permission matrix that decides what a user can view and what a user can change.

Example: a pharmacist can perform checkouts and manage inventory, but should not be able to open the database overview. An admin can manage users and unlock the database overview after re-entering their password.
Role Main Responsibility Typical Access
Admin System governance and control All major modules, user CRUD, RBAC, database overview
Pharmacist Clinical oversight, inventory management, and POS checkout sales. POS, inventory, customers, prescriptions, reports, analytics, and supply chain.

System Architecture

The solution follows a simple three-layer structure:

  1. Frontend: HTML, CSS, and JavaScript rendered in the browser.
  2. Backend API: A Go server that validates requests, applies business rules, and returns JSON.
  3. Database: PostgreSQL stores users, permissions, products, customers, sales, suppliers, purchase orders, and payment audit data.

Plain-language request flow

Step 1: A user clicks a screen such as inventory, checkout, reports, or supply chain.
Step 2: The browser sends a request to the backend, for example /api/products or /api/sales.
Step 3: The backend checks authentication and permissions.
Step 4: The backend reads from or writes to PostgreSQL.
Step 5: The frontend refreshes the screen with real data.

Authentication and Session Flow

Login flow

  1. User enters username and password.
  2. The backend verifies the password hash and confirms the account is active.
  3. The backend issues a signed authentication token.
  4. The frontend stores the token locally and sends it with future API requests.
  5. The app loads the user profile and permission list so it can show only the correct modules.

Logout and re-verification

  1. When a user logs out, the frontend clears the saved token and local session data.
  2. The app returns to the login screen.
  3. The database overview requires an additional password re-entry even for an already logged-in admin.
This second password check protects one of the most sensitive screens in the system.

Checkout and Receipt Flow

Standard sale

Select product: Products are loaded live from the backend catalog.
Add to cart: The cart stores quantity, price, and any prescription details needed.
Choose customer: A walk-in customer can be used, or a saved customer can be linked.
Choose payment: Cash, Card, or M-Pesa.
Submit checkout: The backend verifies stock and records the sale.
Inventory updates: Product stock is reduced automatically.
Receipt generation: The system loads a live receipt from the receipt endpoint.

M-Pesa flow

  1. The pharmacist selects M-Pesa and enters the customer phone number.
  2. The frontend requests an STK push from the backend.
  3. The backend talks to Daraja and stores the payment audit record.
  4. The sale is recorded with a payment reference and a pending or current payment status.
  5. When Daraja sends a callback, the backend updates the payment audit trail and the matching sale payment status.

Supply Chain and Restocking Flow

Supplier management

Supplier records store supplier name, contact person, phone, email, address, and active/inactive status.

Purchase orders

A purchase order connects one supplier to a list of requested products and quantities. It also stores operational status, notes, expected delivery timing, and receiving details.

Receiving stock

Order preparation: Staff create a purchase order manually or from low-stock items.
Supplier delivery: The supplier delivers the requested stock.
Receive action: Staff mark the purchase order as received.
Inventory increase: Product stock is added to the main inventory.
Audit status: The purchase order is locked as received and keeps a receiving trail.
The supply-chain module is meant to support real stock movement, not just display records. It connects planning, ordering, receiving, and inventory updates end to end.

Reports, Analytics, and Database Overview

  • Dashboard: Today’s sales, transactions, prescriptions, and low-stock counts.
  • Reports: Revenue, units sold, inventory value, purchase-order activity, and top products.
  • Analytics: Daily sales trends, category performance, and payment method performance.
  • Database Overview: Plain-language explanations of tables, record counts, and structural details.

Why the database overview exists

The database overview is designed for administrators who need a business-friendly explanation of what data the system stores. It shows table names, table sizes, row counts, column types, and a human explanation of what each table is used for.

This screen is restricted to authorized admins and requires password re-entry before data structure details are shown.

Dynamic RBAC Management

RBAC means Role-Based Access Control. The system now uses a stored permission matrix instead of relying only on fixed hardcoded role rules.

Dynamic

Roles and permissions can be updated without changing application code.

Controlled

Each permission is checked by the backend before protected actions are allowed.

Visible

The frontend uses the user’s permission list to decide which modules are shown.

Deployment and Hosting

The project is prepared for container-based deployment using Docker. The Go backend serves both the API and the frontend web files, while PostgreSQL stores the business data.

  • The backend exposes API routes such as /api/auth/login and /api/sales.
  • The same backend serves the user interface from the web folder.
  • PostgreSQL stores operational data and permissions.

Recommended production pattern

  1. Host PostgreSQL in a secured environment.
  2. Host the Go application behind HTTPS.
  3. Set real environment variables for secrets and callback URLs.
  4. Restrict CORS to the real production domain.
  5. Disable demo seeding in production.

Security and Operational Safety

Password handling

Passwords are stored as hashes, not plain text.

Rate limiting

Authentication endpoints are rate-limited to reduce abuse risk.

Role enforcement

The backend checks permissions before protected actions are allowed.

Database protection

The database overview requires both permission and password re-verification.

Operational stability

Timeouts, request logging, panic recovery, and readiness checks improve stability.

Secrets handling

Credentials should be supplied through environment variables, not committed into tracked files.

Production Readiness Checklist

  • Use a strong JWT_SECRET.
  • Set APP_ENV=production.
  • Set SEED_DEMO_DATA=false.
  • Set ENABLE_PUBLIC_REGISTRATION=false unless self-sign-up is desired.
  • Configure the real database connection.
  • Set the real Daraja callback URL and payment credentials.
  • Use HTTPS for all user traffic.
  • Back up the database regularly.
  • Review RBAC permissions before launch.

FAQ

Can pharmacists see the database overview?

No. That page is restricted to authorized administrators only. Pharmacists handle inventory, sales, prescriptions, and supply chain, but database administration requires the Admin role.

Does a sale reduce inventory automatically?

Yes. Completing a sale updates stock immediately.

Does receiving a purchase order increase stock automatically?

Yes. Receiving stock updates inventory levels.

Can roles be changed later?

Yes. The RBAC screen supports dynamic permission management.

15. Core System Endpoints and Functions Directory

To help you present the project, this section documents all backend Go handlers (API endpoints) and key frontend Javascript functions, explaining their specific business uses and technical implementations.

A. Backend Go Handlers (API Endpoints)

Module / Endpoint Handler Name HTTP Method Description and Business Use Case
Authentication
/api/auth/login		 LoginHandler POST Verifies staff credentials. Compares input password with the stored bcrypt hash. Returns a signed JWT token and user profile details to start a session.
/api/auth/register RegisterHandler POST Creates a new user account (Pharmacist). Hashes the password with bcrypt and inserts the record into the users table. Protected by admin permissions.
/api/auth/me MeHandler GET Extracts the user ID from the active JWT token and fetches the current profile. Used to verify session validity.
/api/auth/logout LogoutHandler POST Logs out the active user session and invalidates the authentication token on the client side.
/api/profile SaveProfileHandler PUT Allows logged-in users to update their full name, username, and change passwords securely.
Products & Catalog
/api/products		 GetProductsHandler GET Retrieves products for sales view. Supports category filtering (e.g. Prescription, OTC, Vitamins) and barcode/name keyword search.
/api/products/{id} ProductItemHandler GET / PUT / DELETE Manages a single product: retrieves details, updates info, or soft-deactivates the item (sets status to 'inactive' so it is hidden but historical sales records are preserved).
/api/admin/products ProductCollectionHandler POST Admin-only endpoint to register a new product, setting details like name, category, brand, price, reorder level, and expiry date.
Inventory
/api/inventory		 GetInventoryHandler GET Lists all active stock levels, batch statuses, and reorder alerts. Highlighted for stock managers and pharmacists.
Sales & Transactions
/api/sales		 ProcessSaleHandler / ListSalesHandler POST / GET POST: Processes POS checkouts. Deducts quantities from inventory (using FIFO logic), links prescriptions for Rx items, computes tax, and inserts records into sales and sale_items tables.
GET: Lists completed transaction summaries.
/api/receipts/{id} GetReceiptHandler GET Generates detailed printable layouts for a completed sale receipt.
Customer Management
/api/customers		 CustomersCollectionHandler GET / POST Lists customer profiles or registers new ones with contact details and loyalty account configurations.
/api/customers/{id} CustomerItemHandler GET / PUT / DELETE Fetches customer info, updates contact or loyalty data, or archives the profile.
Prescription Verification
/api/prescriptions		 PrescriptionsCollectionHandler GET / POST Registers patient prescriptions issued by external doctors. Enforces clinical validation where checkout of prescription (Rx) category products requires linking these IDs.
/api/prescriptions/{id} PrescriptionItemHandler GET Fetches details of a specific prescription, including its items and quantities.
Supply Chain
/api/suppliers		 SuppliersCollectionHandler GET / POST Registers product supply vendors or lists current active suppliers.
/api/purchase-orders PurchaseOrdersCollectionHandler GET / POST Creates purchase orders in 'draft' or 'submitted' status to request inventory items from suppliers.
/api/purchase-orders/{id}/receive ReceivePurchaseOrderHandler POST Receives items from supplier delivery. Transitions PO status to 'received' and automatically increments inventory stock counts.
M-Pesa Payments (Daraja)
/api/payments/config		 PaymentsConfigHandler GET Fetches M-Pesa configurations for the frontend checkout screen.
/api/payments/mpesa/stk-push MPesaSTKPushHandler POST Triggers a mobile STK PIN push to the customer's phone via Safaricom Daraja API. Records transaction state as 'pending'.
/api/payments/mpesa/status/{id} MPesaPaymentStatusHandler GET Queries the current status of an STK push transaction using the Safaricom query API.
/api/payments/mpesa/callback MPesaCallbackHandler POST Public webhook used by Safaricom to report payment outcomes (success/failure), updating tables mpesa_payments and sales.
Database Overview & RBAC
/api/database-overview/access		 VerifyDatabaseAccessHandler POST Verifies admin password / PIN, generating a secure temporary access token (`X-Database-Access-Token`) valid for 10 minutes.
/api/database-overview DatabaseOverviewHandler GET Requires the `X-Database-Access-Token` header. Queries Postgres system catalogs to compile table row counts, sizes, column schemas, and types.
/api/rbac/roles RBACCollectionHandler / RBACRoleHandler GET / PUT Manages the dynamic role-permission access matrix. Adjusts features visible to Admins and Pharmacists.

B. Key Frontend JavaScript Functions

These client-side functions run in the browser to control user interactions, display state variables, and call the Go backend APIs:

  • apiFetch(path, options, auth): Standard network client wrapping the native fetch API. Automatically adds authorization tokens (`Bearer JWT`) to headers and parses responses, throwing helpful toast notifications on failure.
  • bootstrapAuthenticatedApp(): Fired after a successful login. Fetches current session details, parses user roles, applies dynamic permission layouts, and boots core datasets in parallel.
  • loadCoreData(): Triggered on app load. Uses concurrent promises to fetch products, inventory levels, dashboard metrics, customer profiles, dynamic prescriptions, sales history, and database overview parameters.
  • showView(view, event): Coordinates navigation tab state changes. Intercepts clicks, checks if the user's role has permission to access the view, activates a 700ms glassmorphic medicine-pill spinning loader animation, and toggles visibility of the active section while triggering view-specific renders.
  • loadSales(): Fetches the full sales transaction history from the /api/sales endpoint to feed the dashboard's recent transaction tracker.
  • renderDashboardWelcome(): Generates the custom gradient welcome greeting at the top of the dashboard, displaying the active user's full name, role, and context-specific action keys.
  • renderDashboardFeeds(): Renders the real-time operational dashboard widgets: the Recent Transactions feed (top 5 latest sales) and the Expiring Medicines Alert feed (list of active inventory items expiring within 180 days).
  • addToCart(productId): Validates stock availability. If the item is marked prescription-only (Rx), it pops up the verification modal (`#rxModal`) requiring a valid prescription number before adding it to the cart list.
  • unlockDatabaseOverview(event): Triggered when the admin inputs their PIN/password on the Database Overview screen. Posts credentials to /api/database-overview/access, saves the returned access token, and triggers data retrieval.
  • renderDatabaseTables(): Renders rows representing each of the 11 database tables, displaying record totals, column counts, and database memory allocations.
  • showTableSchema(tableName): Compiles column properties for a selected table. Opens the schema modal (`#dbSchemaModal`) listing names, sql data types, and nullable flags.

16. Recent Upgrades & Visual Overhaul (2030 Glassmorphism & Pricing Update)

To make the MedPlus Pharmacy POS system ready for the next decade, a complete visual and operational upgrade has been applied:

A. 2030 Dark Glassmorphism Styling

The old light teal user interface has been transitioned to a high-end 2030 visual design:

  • Radial Background: Uses a rich, deep-slate radial gradient (#0b1329 to #030712) that reduces eye strain and provides a futuristic look.
  • Glass Panel Cards: Content panels use semi-transparent backgrounds (rgba(30, 41, 59, 0.25)) coupled with a backdrop blur filter (backdrop-filter: blur(16px)) and subtle glowing borders.
  • Dynamic Sidebar: Navigations feature glowing hover animations and active neon teal selections.

B. Spinning Medicine Transition Loader

To make page transitions feel smooth and immersive, a custom animation runs when moving between sidebar sections: When a menu option is selected, a 700ms floating page-loader overlays the screen. In the center, a 3D-glowing medicine pill icon rotates smoothly (@keyframes loaderSpin) with a floating bounce (@keyframes loaderFloat) and pulsing teal background glow (@keyframes loaderGlowPulse).

C. Realistic Whole Integer Ksh Pricing

The system has been updated from a decimal-based dollar pricing scheme to a realistic integer-based Kenyan Shilling (Ksh) pricing model:

  • No Decimals / Cents: Cents have been completely removed from frontend displays (formatted via Math.round in JS) and backend seeds. A product price will show as Ksh 450 instead of 4.99.
  • Database Migration: On database startup, a pricing migration automatically rounds all existing product prices using ROUND() and converts any low dollar-equivalent prices to their realistic Kenyan Shilling equivalent.
  • Restocking Costs: Auto-generated restock orders round purchase costs to the nearest integer using Math.round(price * 0.7), ensuring integer consistency across supply chain calculations.
